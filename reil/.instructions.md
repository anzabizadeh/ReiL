# ReiL Core Architecture Instructions

This document is designed for AI assistants working with the ReiL codebase. It explains the fundamental architecture, core abstractions, and patterns you'll encounter when building or modifying ReiL components.

## Architecture Overview

ReiL is a hierarchical, extensible reinforcement learning framework built on three architectural layers:

### Layer 1: ReilBase (Foundation)
**File**: [reil/reilbase.py](reil/reilbase.py)

The base class for all ReiL objects. Provides:
- **Naming & Pathing**: Objects can be saved/loaded with automatic path management
- **Logging**: Each ReilBase instance has its own logger (configured via `logger_name`, `logger_level`, `logger_filename`)
- **Serialization**: Objects can be persisted with `save()` / `load()` methods; uses custom pickle-based format (see [serialization.py](reil/serialization.py) for backward compatibility details)
- **Persistent Attributes**: Specified attributes survive across load operations (useful for preserving metadata across serialization)

**Key Pattern**: When creating new classes, inherit from ReilBase if they need persistence, logging, or naming capabilities.

### Layer 2: Stateful (Entity Management)
**File**: [reil/stateful.py](reil/stateful.py)

Extends ReilBase for entities that maintain state. Stateful provides:
- **State Management**: State is represented as a `FeatureSet` (see below) with pluggable state definitions
- **Entity Registration**: Track related agents (for subjects) or subjects (for agents) via `register()` / `deregister()`
- **Statistics**: Compute statistics over trajectories using `statistic.add_definition()` and `statistic(<id>, <name>)`
- **Sub-Components Extraction**: Automatically discover and manage nested ReiL objects via `_sub_comp_*` methods

**Key Pattern**: Stateful entities (Agent, Subject, Environment) all follow this pattern. They track relationships, manage state definitions dynamically, and can dump state/trajectories.

### Layer 3: Domain-Specific Implementations
Built on Stateful, these classes implement the RL workflow:
- **Agent** ([reil/agents/agent.py](reil/agents/agent.py)): Learnable agent with exploration strategy, learner, and training trigger
- **Subject** ([reil/subjects/subject.py](reil/subjects/subject.py)): Stateful environment entity (e.g., patient, game state)
- **Environment** ([reil/environments/](reil/environments/)): Orchestrates agent-subject interactions (Sequential, Single, Task variants)

## Core Abstractions

### Feature & FeatureSet
**File**: [reil/datatypes/feature.py](reil/datatypes/feature.py)

**Feature**: Immutable dataclass representing a single data point with metadata:
- **Numerical**: Has `value` in range `[lower, upper]`, optionally `normalized` to `[0, 1]`
- **Categorical**: Has `value` from `categories` tuple, optionally `normalized` (one-hot or integer encoded)
- **Missing**: Value can be `MISSING` to represent absent data; handled gracefully in downstream processing

**FeatureSet**: Dictionary-like container of Feature objects. Core communication format in ReiL:
- Used for **states** (agent observation, subject situation)
- Used for **actions** (agent decision, subject dosing)
- Used for **rewards** (scalar reward passed back through environment)
- Supports iteration, key lookup, and serialization

**Key Pattern**: Always build state, action, and reward representations using Feature/FeatureSet. This ensures:
- Proper type/range checking (numerical vs. categorical bounds)
- Normalization consistency (critical for neural networks)
- Missing value handling (graceful degradation)
- Trajectory dumping/serialization

### Agent
**File**: [reil/agents/agent.py](reil/agents/agent.py)

Core attributes:
- **Learner**: Learns from (state, action, reward, next_state) tuples
- **Exploration Strategy**: Epsilon-greedy or custom; determines exploration vs. exploitation
- **Discount Factor**: `γ` for future reward weighting
- **Training Trigger**: When to call `learn()` (`'termination'`, `'state'`, `'action'`, `'reward'`, `'none'`)

**Key Pattern**: Agents are typically instantiated from YAML config via [yaml_tools.py](reil/utils/yaml_tools.py). The config specifies learner, buffer, exploration strategy. At runtime, agents observe states and execute actions.

### Subject
**File**: [reil/subjects/subject.py](reil/subjects/subject.py)

Core attributes:
- **State Definition**: What features constitute the state (e.g., patient INR, warfarin level)
- **Entity Registration**: Which agents interact with this subject
- **State Dumper**: Optional trajectory logger to record (state, action, reward) sequences
- **Modifiers**: Demons that alter state (used for research intervention simulations)

**Key Pattern**: Subjects encapsulate domain logic (PK/PD models for Warfarin, game rules for gym). They respond to actions with rewards and state transitions.

### Environment
**File**: [reil/environments/](reil/environments/)

Orchestrates agent-subject interaction:
- **Sequential**: Multiple subjects, one per timestep
- **Single**: Single subject repeatedly stepped
- **Task**: Subject-specific task completion logic

**Key Pattern**: Environments manage the training loop. They step subjects, collect trajectories, and trigger agent learning.

### Learner
**File**: [reil/learners/learner.py](reil/learners/learner.py)

Abstract interface for learning algorithms. Implementations include:
- **QLearner**: Deep Q-learning with model, buffer, target network
- **PPOLearner**: Proximal Policy Optimization
- **A2CLearner**: Actor-Critic

**Key Pattern**: Learners implement `learn(inputs, targets)` where inputs are (state, action) and targets are Q-values, policy gradient, etc. They manage model checkpoints and logging.

## Configuration & Instantiation Patterns

ReiL uses YAML-based configuration to dynamically instantiate objects. Understanding this pattern is critical for both usage and extension.

### Config Structure
Example from [warfarin_dosing/configs/agents.yaml](warfarin_dosing/configs/agents.yaml):

```yaml
dqn_agent_setting: &dqn_agent_setting
  reil.agents.deep_q_learning.DeepQLearning:
    name: deep_q
    learner:
      reil.learners.q_learner.QLearner:
        model:
          reil.learners.q_learner.DeepQModel:
            learning_rate: 1e-3
            hidden_layer_sizes: [256, 128, 64, 32]
        tensorboard_filename: $h$_$action$$sdemon$
        tensorboard_path: ./logs
    buffer:
      reil.datatypes.buffers.vanilla_experience_replay.VanillaExperienceReplay:
        buffer_size: 450
        batch_size: 50
    exploration_strategy:
      reil.utils.exploration_strategies.VariableEpsilonGreedy:
        epsilon: "lambda n: 1/(1+n)"
    discount_factor: 0.95
```

**Instantiation Process** (via [yaml_tools.py](reil/utils/yaml_tools.py)):
1. Parse YAML dict where keys are fully-qualified class names
2. Look up class via `importlib` (e.g., `reil.agents.deep_q_learning.DeepQLearning`)
3. Recursively instantiate nested objects (learner, buffer, exploration_strategy)
4. Call `ClassName(**config_dict)` to construct the object
5. Support variable substitution (e.g., `$h$`, `$action$`) for dynamic naming

**Key Patterns**:
- YAML anchors (`&name`, `<<: *name`) allow config reuse and inheritance
- Nested dicts become nested object instantiation
- Lambda expressions (e.g., `lambda n: 1/(1+n)`) are evaluated for functional parameters
- Variable placeholders enable dynamic configuration at runtime

## Serialization & Backward Compatibility

ReiL objects can be saved and loaded with automatic backward compatibility.

**Files**: [serialization.py](reil/serialization.py), [reilbase.py](reil/reilbase.py#L90-L115)

**Key Mechanism**:
- Objects inherit from ReilBase, which provides `save()` and `load()` methods
- `save()` uses custom pickle (optionally BZ2-compressed)
- `load()` uses `CustomUnPickler` that maps old class paths to new ones if classes have been renamed/moved
- Persistent attributes (specified at init) survive load operations

**Critical for Extension**: When refactoring ReiL internals (renaming classes, moving modules), update the unpickler mapping in [serialization.py](reil/serialization.py) to maintain compatibility with legacy saved models.

## Extension Points

### Adding a Custom Agent
1. Inherit from `Agent` (or `BaseAgent` if non-learning)
2. Implement `act(state: FeatureSet) -> FeatureSet` method (inherited, uses learner)
3. Optionally override `observe()` for custom learning triggers
4. Instantiate via YAML config or directly in Python

### Adding a Custom Subject
1. Inherit from `Subject`
2. Define state via `self.state.add_definition()` in `__init__`
3. Implement `step(action: FeatureSet) -> tuple[FeatureSet, float]` (returns next_state, reward)
4. Optionally add modifiers via `Modifier` for demons

### Adding a Custom Learner
1. Inherit from `Learner` (or `LearnerProtocol` for duck typing)
2. Implement `learn(inputs, targets) -> None`
3. Manage model checkpoints via `save_checkpoint()` / `load_checkpoint()`
4. Integrate with TensorFlow or PyTorch as needed

### Adding a Custom Environment
1. Inherit from base Environment class
2. Implement interaction loop (step subjects, collect trajectories)
3. Integrate with agent learning triggers

## Common Pitfalls

### State Shape Mismatches
**Problem**: Feature dimensions don't match between state definition and learner input.  
**Solution**: Ensure your state dumper or Feature definition includes all expected features. Validate in Subject's `step()` method.

### Feature Normalization Inconsistency
**Problem**: Numerical features not normalized `[0, 1]`, causing numerical instability in neural networks.  
**Solution**: When defining numerical features, always specify `lower` and `upper` bounds. Feature creation via config automatically normalizes.

### Missing Value Handling
**Problem**: `MISSING` values cause crashes downstream.  
**Solution**: Use `Feature.categorical()` with explicit categories or handle missing values gracefully in feature extractors. See [feature.py](reil/datatypes/feature.py) for `NoneFeature` patterns.

### Serialization Breakage
**Problem**: Renamed classes / moved modules cause `CustomUnPickler` to fail.  
**Solution**: Update unpickler mapping in [serialization.py](reil/serialization.py) before deploying changes that affect class paths.
